## 第 0 章 总览

### 0.1 一句话定位
一个 Windows 桌面 GUI（PySide6/Qt），是 **A 端（ChatGPT）↔ 执行端（B 端）** 之间的**剪贴板中继器**：
- A 端把 `AI_RELAY/1` 文本任务写入剪贴板；
- B 端**监听剪贴板** → 解析 → 认领（落盘 `tasks.json`，带单调序号）→ 按 `TARGET` 路由给**执行端**跑；
- 执行端只有两个：**Reasonix**（Windows 桌面 UI 自动化）与 **OpenChamber**（本地 HTTP 服务）；
- B 端拿到执行端结果后，用**原 `TASK_ID`** 包装成 `RESPONSE` 写回剪贴板交给 A 端。
- 若中断/失败/停止，B 端必须给 A 端一个**结构化失败 RESPONSE**（绝不静默）；重复的 `TASK_ID` **永不重跑**（回已有状态/回复）。

### 0.4 核心不变量（Invariants，代码注释里反复标注 1~8）
1. **A 端任务永不因窗口忙碌被拒绝**：被接受即同步落盘（`tasks.json` + 单调 `sequence`），要么立即跑，要么进**持久 FIFO 队列**按顺序跑；程序重启也不丢。
2. **A 端优先级**：A 端（来源 CHATGPT）任务占用某目录/会话时，**手动监控让出“回复包装权”**（最终回复归 A 端任务流程），但**继续做停滞检测与自动续接**（会话健康仍由监控负责）。
3. **会话所有权可被轮换替换，但归属不变**：轮换换会话不换 owner，新旧会话都登记为 in-flight。
4. **最终回复永远绑定原 `TASK_ID`**，绝不绑定 `manual-*` 临时 id。
5. **每个任务都落到终态**（COMPLETED / FAILED / STOPPED_BY_USER / RECOVERY_REQUIRED）；启动时对上次的非终态记录做**只读对账**（不重发）。
6. **重复 `TASK_ID` 永不重跑**：回已有状态或已保存回复，且仍绑定原 id。
7. **停止/失败都是终态结果**：A 端收到结构化 RESPONSE（`IN_REPLY_TO=原 TASK_ID`），绝不静默停止。
8. **终态保护**：任务到达任一终态后，迟到的普通 worker 写入（`mark_if_active`）一律 no-op；只有显式“重入”（`mark_reentry`：手动继续 / 新会话重试 / 停止中断任务 / 启动对账）才能再移动它。

## 第 1 章 剪贴板协议（“怎么接收”的基础）

### 1.1 常量（`protocol.py:10-12`）
- `PROTOCOL_MARKER = "AI_RELAY/1"`（V1 首行）
- `LEGACY_BEGIN = "----- AI_RELAY_BEGIN -----"` / `LEGACY_END = "----- AI_RELAY_END -----"`

### 1.2 V1 格式（字节级）
```
AI_RELAY/1
MESSAGE_ID: <uuid 或任务id>
SOURCE: CHATGPT|EXECUTOR
TARGET: REASONIX|OPENCHAMBER|EXECUTOR
TYPE: TASK|RESPONSE
[IN_REPLY_TO: <TASK_ID>]      # 仅 RESPONSE 有
[ROUND: <int>]                 # 默认 0
[MAX_ROUNDS: <int>]            # 默认 3
[WORKDIR: <dir>]               # 可选
<空行>
<正文 body，逐字保留>
```
解析规则（`parse_message`, `protocol.py:43`）：
1. `\r\n`→`\n`；若以 `LEGACY_BEGIN` 开头走 legacy 分支；否则按**第一个空行**切成 header / body。
2. 首行必须 `== "AI_RELAY/1"`，否则 `missing AI_RELAY/1 marker`；必须有空行分隔，否则 `missing blank line`。
3. 其余 header 行按 `KEY: value` 解析（key 大写、去空白）；缺冒号/空值/重复 key 都报错。
4. 必填 `MESSAGE_ID / SOURCE / TARGET / TYPE`，缺一报 `missing protocol headers`；body 不能空白。
5. `TYPE` 必须能映射成 `MessageType`（TASK/RESPONSE），否则 `unsupported message type`。
6. `ROUND/MAX_ROUNDS` 必须是整数且 `0<=ROUND<=MAX_ROUNDS`、`MAX_ROUNDS>=1`。

### 1.3 legacy_web 格式（`_parse_legacy_web_message`, `protocol.py:145`）
```
----- AI_RELAY_BEGIN -----
SOURCE: CHATGPT
TARGET: REASONIX
TYPE: TASK
TASK_ID: <id>
[ROUND: n] [MAX_ROUNDS: m]
CONTENT:
<正文，可多行>
----- AI_RELAY_END -----
```
`message_id` 取 `TASK_ID`；`protocol_format=LEGACY_WEB`。

### 1.4 封装 RESPONSE（`wrap_response`, `protocol.py:98`）
- 校验：body 非空、`in_reply_to` 非空、`0<=ROUND<=MAX_ROUNDS`、`MAX_ROUNDS>=1`。
- **V1 输出**：`AI_RELAY/1` + `MESSAGE_ID:<新uuid>` + `IN_REPLY_TO:<原TASK_ID>` + `SOURCE:EXECUTOR` + `TARGET:CHATGPT` + `TYPE:RESPONSE` + `ROUND` + `MAX_ROUNDS` + 空行 + body。
- **legacy 输出**：`LEGACY_BEGIN` + `SOURCE:EXECUTOR` + `TARGET:CHATGPT` + `TYPE:RESPONSE` + `TASK_ID:<原id>` + `ROUND` + `MAX_ROUNDS` + `TIME:<本地时间>` + `CONTENT:` + body + `LEGACY_END`。
- 关键点：**`IN_REPLY_TO`/`TASK_ID` 永远是原始任务 id**，`MESSAGE_ID` 是新生成的响应 id（`manual-*` 只在“手动包装/监控包装”时用）。

### 1.5 剪贴板监听器（`ClipboardListener`, `clipboard.py:14`）
- 信号 `task_received(str)`。
- 自写保护：`write_response(text)` 会先算 `sha256` 摘要并存 `_self_write_digest`/`_last_seen_digest` 再 `clipboard.setText`；`_on_changed` 里若新摘要等于 `_self_write_digest` 或 `_last_seen_digest` 就**忽略**（防止自己写回的响应又被当成新任务，防重放/防抖动）。
- 启动 `start()`：记录当前剪贴板摘要作基线、置 `_enabled=True`；`pause()`：`_enabled=False`（关闭后 `_on_changed` 直接返回）。
- `looks_like_relay_message(text)`（静态）：去 `\r\n`、lstrip 后是否以 `AI_RELAY/1` 或 `LEGACY_BEGIN` 开头 —— 只有像协议内容的才进入 `task_received`。
- **接收链路**：`clipboard.dataChanged` → `_on_changed`（去重/自写过滤）→ `task_received` → 窗口 `_on_clipboard_text`（`ui.py:2019`）。

## 第 3 章 每个按钮的功能详解

> 每个按钮按【何时可用】【判断逻辑】【怎么验证】【接收/发送】四段写。
> “验证”分两部分：**手动验证**（在真实环境怎么点、看什么）和**自动验证**（对应 `tests/` 的哪个用例、断言什么）。

### 3.1 「启动任务接收」(`start_button` → `_start`, `ui.py:1294`)
- **何时可用**：`enabled and not listener.enabled`（未监听时可点）。
- **判断逻辑**：调 `_ensure_clipboard_listener_started("manual")`（幂等启动 `ClipboardListener`）；成功→状态「空闲：正在监听剪贴板」；失败→`_update_runtime_status`。同时 `QTimer.singleShot(0, …)` 已在窗口构造时触发监听启动/自检/启动对账。
- **怎么验证**：
  - 手动：点它后 `_clipboard_status_label` 变绿「任务接收：运行中」，`start` 置灰、`pause` 变亮；把一段 `AI_RELAY/1` 任务粘到剪贴板，窗口立即拾取并进入 `task_label`。
  - 自动：`tests/test_ui_startup.py`（监听启动/自检/按钮态）。
- **接收**：监听器 `task_received` → `_on_clipboard_text` → 见 5.1。

### 3.2 「暂停任务接收」(`pause_button` → `_pause`)
- **何时可用**：`enabled and listener.enabled`。
- **判断逻辑**：`listener.pause()`（`_enabled=False`，之后剪贴板变化不再触发）；`_clipboard_paused=True`；状态置「已暂停」。**注意**：暂停只是停止“新任务拾取”，不影响正在执行的任务与监控。
- **怎么验证**：手动——暂停后粘贴新任务不再被拾取；再点「启动」恢复。自动：`test_ui_startup.py`。

### 3.3 「测试 Reasonix 连接」(`check_button` → `_self_check`, `ui.py:2932`)
- **何时可用**：`enabled`（不忙时）。
- **判断逻辑**：置忙、快照 `detail_label`，起 `SelfCheckTask` → `reasonix.self_check()` 返回 `{检查项: 通过?}`；有任一失败→`failed("自检未通过: …")`→`_task_failed`；全通过→`_self_check_succeeded`。启动时（`_startup_check_pending=True`）该检查是**信息性**的：失败不阻塞 OpenChamber 监控，仅提示「REASONIX 任务将失败，OPENCHAMBER 不受影响」，并继续 `_auto_start_after_self_check`。
- **怎么验证**：手动——Reasonix 窗口开着时点它，详情显示「窗口、输入框和发送按钮均可通过 UIA 识别」；关掉 Reasonix 则失败。自动：`test_ui_startup.py`（用 fake Reasonix）。
- 关键细节：`_self_check_succeeded` 只在“无人抢占详情区”时才覆盖详情（`authoritative` 判定 `ui.py:2956`），避免自检结果盖掉更高优先级的任务/监控文案。

### 3.4 「监控 OpenChamber」(`monitor_button` → `_toggle_monitor` / `_start_monitor` / `_stop_monitor`, `ui.py:1355/1439/1552`)
- **何时可用**：`enabled`（`_stopping` 期间点击被忽略，按钮保持禁用直到收尾完成）。点击在 start/stop 间切换。
- **切换逻辑**（`_toggle_monitor`）：`_stopping`→忽略；`active`→`_stop_monitor`；否则→先 `_ensure_clipboard_listener_started("monitor")`（**若任务接收处于暂停/未启动会自动恢复任务接收**，并提示「任务接收当前已暂停，已同时重新启动」）→ 再 `_start_monitor`。
- **启动判断逻辑**（`_start_monitor`）：
  1. 若上一次监控还在收尾（`_oc_monitor_stopping or _monitor_workers`）→ 提示「等待上一次监听完全停止」，直接返回（新旧代次永不重叠）。
  2. 校验：`directory` 必填且是**存在的文件夹**（`_directory_is_valid`）；`session_id` 必填；用 `client.session_exists(session_id, directory)` 校验会话存在（失败→`_show_error`，不启动）。
  3. 计算基线：`scan = monitor_scan(…)`，`baseline = scan.completed_history_ids`（**只把“已完整完成”的历史回复**作基线；仍在流式中的消息不进基线，之后完成仍能被包装）。
  4. 置 `_oc_monitor_active=True`、`_monitor_generation+=1`，重置所有 auto/interrupt/transport 状态；`monitor_button` 文案变「停止监控 OpenChamber」；起 `MonitorPollTask`（见 4.8）。
- **停止判断逻辑**（`_stop_monitor`/`_finish_monitor_stop`）：异步收尾——置 `_stopping`、`generation+=1`、`stop_event.set()`，**只有最后一个 worker 发 `finished`** 才在主线程复位全部状态、按钮还原。会话与历史**全保留**（停止不删会话）。
- **怎么验证**：
  - 手动：填好目录+选一个存在会话→点它，`_monitor_status_label` 变绿「运行中」，状态「正在监听…会话 xxx」；会话出现新的已完成回复→自动包装写剪贴板；会话卡住→见 3.6/4.8 的中断提示。
  - 自动：`test_oc_monitor.py`（B 端任务 + 监控自动续接 1/3 完成且不产生 `manual-*`）、`test_interruption_recovery.py`。
- **接收/发送**：新完成回复 → `_on_monitor_reply`（见 4.8）；中断 → `_on_monitor_interrupted`（见 4.8）。

### 3.5 「包装内容」(`wrap_button` → `_wrap_clipboard_content`, `ui.py:3065`)
- **何时可用**：`enabled`。
- **判断逻辑**：

## 第 4 章 核心判定逻辑（引擎层）

### 4.1 任务路由（`RelayWorkflow.process`, `relay.py:426`）
进入即：`current_session=None`、`recovery_attempted=False`、清 `pending_continue/pending_rejection/failure_response`（新任务作废旧任务的恢复槽）。然后：
1. `parse_message(text)`；
2. `source != CHATGPT` → `_finalize_failure(FAILED,"unsupported task source")` + raise；
3. `target ∉ KNOWN_TARGETS{REASONIX,OPENCHAMBER,EXECUTOR}` → FAILED + raise；
4. `message_type != TASK` → FAILED + raise；
5. `registry.record(id)` 已存在且非 `RECEIVED` → `task was already processed`（重复，正常不该走到，UI 已先答）；
6. 路由：`resolve_executor_kind` → OPENCHAMBER 走 `_run_openchamber`，否则 `_run_reasonix`。
7. `RelayProtocolError` → `invalid clipboard task`。

`_run_reasonix`：`mark_if_active(PROCESSING)` → `reasonix.execute(body)` → `wrap_response`（用原 format/round/max_rounds）→ `save_reply` → `mark_if_active(COMPLETED)` → 返回 response；异常 → `_finalize_failure(FAILED)` + re-raise。

### 4.2 OpenChamber 执行流程（`_run_openchamber`, `relay.py:535`）
1. `directory = task.workdir or settings.openchamber_directory`；空→FAILED(missing directory)；目录不存在（且非注入 client）→FAILED。
2. 解析会话：`settings.openchamber_sessions[目录key]`；若无且该目录是默认目录→回退 `openchamber_session_id`。
3. `client.verify()`（`/health`，`status==ok`）。
4. 有会话→`session_exists` 校验（不存在则置空）；无会话→`create_session("AI Relay - <项目名>", dir)` 并持久化到 `openchamber_sessions`/默认 `openchamber_session_id` + `settings.save()`。
5. `mark_if_active(PROCESSING, executor, session_id, directory)`；构造 `current_session=TaskOutcome(...)` → `session_callback`（UI 点亮“打开会话”）。
6. `client.open_session(session_id)`（深链；失败**不发送**）。
7. `tagged_prompt = body + "\n\n[AI_RELAY_TASK_ID: 原id]"`（把任务 id 打进 prompt，便于事后定位轮次）。
8. `client.send(...)`（见 4.11）：
   - `OpenChamberModelRequestRejectedError` → `_note_model_rejection` + 抛（带 `MODEL_REJECTION_PROMPT`）→ UI 点亮「新会话重试」；
   - `OpenChamberBadRequestError`（普通 400，无 isRetryable=false）→ 抛（不自动恢复、无新会话重试）；
   - 成功→`mark_if_active(PROCESSING, requested_model, resolved_model)`；若 `resolved_model != 请求`→提示模型不一致。
9. `wait_for_completion(client, dispatch, completion_timeout, poll_interval, grace=5, status_callback, cancel_event)`（见 4.3）：
   - `ModelRequestRejectedError`→`_note_model_rejection`+抛；
   - `OpenChamberInterruptedError`→`_auto_recover`（见 4.6）：返回 None 则抛 `AR_RECOVERY_FAILED`；否则用恢复结果继续；
   - 成功→`_complete_openchamber_result`（见下）。
10. 异常出口：`OpenChamberCancelledError`→`_finalize_failure(STOPPED_BY_USER)`+清 pending+raise `CANCELLED_MARKER`；其它→模型拒绝时只 `mark_if_active(FAILED)`（非终态，仍可新会话重试）否则 `_finalize_failure(FAILED)`。

`_complete_openchamber_result`（`relay.py:950`）：`model_details` 算三层模型与 mismatch 提示 → `wrap_response(final_text, 原id, 原format/round/max_rounds)` → `save_reply` → `mark_if_active(COMPLETED, …含 requested/resolved/actual_model, model_note)` → `outcome`/`current_session` → 对本轮**每条** assistant 消息 `mark_message_wrapped`（监控永不重复包装）→ 清 `pending_continue`。

### 4.3 完成判定 `wait_for_completion`（`openchamber.py:1699`）
**“完成”必须同时满足全部**：
- 会话状态是**已确认的 idle**（显式 idle，或“曾活动后从状态表消失”=服务端 idle）；**未识别状态/接口失败/坏负载绝不转成 idle 或成功**；
- 轮次能**唯一定位**（`locate_round`：非 ambiguous、非 not_found）；
- 本轮最后一条 assistant 消息：`time.completed` 是**正整数**（0/负/布尔都拒绝）、无 `info.error`、`finish=="stop"`、无“待定 tool/权限 part”、有**非空最终文本**。
- `finish=="length"`（被输出上限截断）与 error → **按失败报，绝不包装成成功**。

**轮询主循环**（每轮）：
1. `cancel_event` 置位 → `OpenChamberCancelledError`（不碰会话）；
2. 超过 `deadline`（`timeout<=0` 表示永等，`deadline=inf`）→ `OpenChamberTimeoutError`（会话仍在跑，提示去 OpenChamber 看）；
3. 取状态：`status_fn = client.session_status_detail`（有则用它，否则 `session_status`）。
   - `ModelRequestRejectedError`→直接抛；
   - `OpenChamberUnavailableError`→`_transport_failure`（见 4.5）continue；
   - 其它 `OpenChamberError`→`status_type="unknown"`；
   - 成功读到→`transport_retry_count=0`。
4. **状态分支**：
   - `busy/retry`→活动（`session_activity_observed=True`，清 idle 计数/各 grace 期限）；若 `round_has_pending_user_action`→提示「请在 OpenChamber 中处理」，否则显示工作中（`timeout<=0` 显示“无时间限制”）；sleep 后 continue。
   - `missing_from_status_map 且 未活动`→**不是卡死**（首轮/服务重启/状态滞后）→仅等待，不启动 idle 确认。
   - `status_type ∉ {idle, missing}`（未知/坏）→等待，不转成功。
   - **idle 或（活动后）missing**→`status_is_missing` 标记，读消息：
     - `locate_round`：`ambiguous`→`OpenChamberSessionError`（不猜）；`not_found`→`record_grace`（5s）等待，超时→“从未被记录”失败；定位成功→`session_activity_observed=True`。
     - `_round_assistant_messages` + `_follow_continuation_chain`（把 `finish=tool-calls` 后监控自动续接产生的新 user→assistant 链并入本轮，使其能发现最终回复）。
     - 无 assistant 消息→`reply_grace`(5s) 等待，超时→`_note_idle_suspicion("no_assistant_reply" / "status_missing_after_activity")`。
     - 有新 assistant 消息→重设 `incomplete_grace`、记录 `last_seen_message_id`；**本轮可观测状态签名**（`last_message_id, finish, 最终文本长度, 工具调用数`）变化=活动→`session_activity_observed=True`+清 idle 计数（流式/增长不算卡死）。
     - `has_pending_user_action`→提示处理、继续等。
     - `info.error`：`detail` 是 `bad request`/`uri too long`→`OpenChamberModelRequestRejectedError`（414/400, isRetryable=False）；否则 `OpenChamberSessionError`。
     - **未完成**（`completed` 非正整数）→`incomplete_grace`(5s) 等待，超时→`_note_idle_suspicion("not_completed" / "status_missing_after_activity")`。
     - `finish=="length"`→`OpenChamberSessionError`（截断，非成功）。
     - `finish=="tool-calls"`：若 `status_is_missing`→`missing_tool_grace`(5s) 等待，超时→`_note_idle_suspicion("status_missing_after_activity")`；否则继续等工具后续回复。
     - `finish` 非 stop：为 None→`_note_idle_suspicion("finish_none" / "status_missing_after_activity")`；其它→`OpenChamberSessionError`。
     - `finish=="stop"` 但无最终文本→`_note_idle_suspicion("no_final_text" / "status_missing_after_activity")`。
     - 全通过→取 `actual_model`、`reference_model=resolved or requested or actual`、`model_mismatch` → 返回 `CompletionResult(...)`。

> **`missing_from_status_map` 语义**（`session_status_detail`, `openchamber.py:732`）：状态请求**成功**但会话不在返回 map 里（该 map 只放 busy/retry 条目）→服务端视为 idle，但客户端**不得**与 `unknown`（请求失败/不可解析）或显式 idle 混淆：只有**先观察到活动**的会话，消失后才按 idle 处理。传输层失败（SSE 超时/连接重置，表现为 `OpenChamberUnavailableError`）与 HTTP 错误是 **raise**，不是 missing。

### 4.4 异常中断判定：3 次连续确认（`_note_idle_suspicion`, `openchamber.py:1830`）
- 传入 `reason` 与 `signature`（异常 idle 的指纹，如 `("not_completed", last_message_id, finish, final_len)`）。
- 若 `signature` 变化/首次→`idle_confirmations=1`、`idle_signature=signature`，提示「异常 idle 连续确认：1/3」。
- 若 `signature` 不变→`idle_confirmations+=1`，提示 `n/3`；达到 `REQUIRED_IDLE_CONFIRMATIONS=3`→`raise OpenChamberInterruptedError`（带 session_id/last_message_id/last_finish/reason）。
- **作用**：任何一轮的可观测状态一变（新消息/文本增长/finish 变/完成）都会在上层重置计数，防止流式过程中的短暂 idle 抖动误判。

### 4.5 传输层有限重连（`_transport_failure`, `openchamber.py:1795`）
`OpenChamberUnavailableError`（SSE 读超时/连接重置/服务不可达）：
- `transport_retry_count+1`；`<= MAX_TRANSPORT_RETRIES(2)`→按 `TRANSPORT_RETRY_DELAYS=(3.0,8.0)` 可取消地 sleep、提示「重连 n/2」，返回（continue 下一轮）。
- 超过→`raise OpenChamberInterruptedError(reason="transport_failure")`（进入 4.6 恢复，或转人工）。
- **绝不重发原任务、绝不建新会话**。每次成功读取后 `transport_retry_count=0`。

### 4.6 自动恢复 `_auto_recover`（`relay.py:760`）——“relay 一次性续接 1/1”
触发：`wait_for_completion` 抛 `OpenChamberInterruptedError`。
1. 若 `recovery_attempted`（已用掉一次性额度）→ 提示 `AR_RECOVERY_FAILED`，返回 None（保留 `pending_continue` 给人工）。
2. **立即**设 `pending_continue=OpenChamberContinue(message, session, dir, agent, model)`（这样即使自动恢复失败，UI 也点亮「继续当前任务」）。
3. **先等约 10s（`RECOVERY_DELAY_SECONDS`）复查**会话是否**自行恢复**：循环里若 `status ∈ {busy,retry}`→用**原始 dispatch** `wait_for_completion` 等它自己出结果，**不消耗**一次性额度（返回该结果）。
4. 10s 后：
   - `status ∉ {idle, missing}`→`AR_RECOVERY_FAILED`，返回 None。
   - idle→读消息，若**监控已续接**（存在不在 `original_dispatch.pre_send_message_ids` 里的新用户消息）→用原始 dispatch `wait_for_completion`（`_follow_continuation_chain` 跟踪监控续接链），不重复发。
   - 否则→`recovery_attempted=True`，`client.send(OPENCHAMBER_CONTINUE_PROMPT, 原agent/model)` → `wait_for_completion`；若**再次**中断/400→`AR_RECOVERY_FAILED`，返回 None（保留 pending 给人工）。
- 常量：`OPENCHAMBER_CONTINUE_PROMPT`（`relay.py:54`）要求“从最后未完成步骤继续，勿重复已完成，返回完整中文最终报告”。

### 4.7 模型拒绝 → 新会话重试
- 识别（`openchamber.py:886-940`）：HTTP 400 的 detail 里若含结构化 `isRetryable`→**以它为准**（`false` 即拒绝）；若无结构化字段，需同时出现 `APIError` 标记 + `request_url` + `statusCode==400` 才当“模型拒绝”（**普通 400 绝不被误降级**）。
- 流程见 3.7：`_note_model_rejection` 存 `pending_rejection`→UI 点亮「新会话重试」→`retry_model_rejected_task` 建**全新**会话重发；再次拒绝→`MODEL_REJECTION_AGAIN`（终态）。

### 4.8 手动监控轮询（`MonitorPollTask._pump`, `ui.py:501` + `MonitorRoundTracker.step`, `openchamber.py:1567`）
**基线**：`baseline=启动时 completed_history_ids`；`tracker.reset_round(baseline, "monitor_start")`。
**每轮**：`probe = monitor_probe(client, session, dir, frozenset(seen))`（一次 messages + 一次 status；status 归一化：missing→idle，非 idle/busy/retry→unknown）。
- **传输失败**：`OpenChamberUnavailableError` 且 `transport_failures < MONITOR_MAX_TRANSPORT_RETRIES(2)`→按 `MONITOR_TRANSPORT_RETRY_DELAYS=(3,8)` 重连；超过→`transport_error`（状态“暂无法确认”，保持轮询直到 `transport_recovered`）。非传输错误→`failed` 后继续轮询（不杀监控）。
- **包装新回复**：遍历 `probe.new_completed`（`_message_completed`：`time.completed` 正整数 + `finish==stop` + 无 error + 非空文本），跳过已 `is_message_wrapped`/已 seen 的 → `reply.emit(text, msg_id)` → `seen.add` → **本轮包装过**则 `tracker.reset_round(probe.seen_ids, "wrapped_final_reply")` 冷启动下一轮（之后历史 idle 不再报警）。
- **轮次检测**（`tracker.step`）：
  - `new_ids`（本轮新消息）或“同消息文本增长”或 `status∈{busy,retry}`→**activity**（`activity_observed=True`、清 `idle_confirmations`、清 `interruption_emitted`）。
  - 从未活动 + idle→`no_activity_since_baseline`（纯历史会话永不触发）。
  - 已活动 + idle→检查**本轮**消息（去掉基线）是否有“嫌疑”：最后 assistant `finish==tool-calls` / 出现空 assistant / 最后 assistant `completed_ts is None` / `finish is None` / 本轮有工具调用。无嫌疑→`idle_without_suspicion`（清零）；有嫌疑且未已报→`idle_confirmations+=1`，达 `required_idle=MONITOR_ONLY_IDLE_CONFIRMATIONS(3)`→`event="interrupted"`（reason=`monitor_idle_without_completed_reply`）。
  - **busy 无进展**（`ui.py:613`）：`busy_reset_event`（手动/自动续接成功后置位）→清零计时；否则签名 `(latest.message_id, text_length, finish, tool_count)` + `seen_ids` 集合**完全不变**持续 `busy_stale_log_interval(30s)`→周期性写“仍 busy 但无进展”日志（只作证据，不自动恢复）；持续 `busy_without_progress_threshold(120s)`→**每卡死段最多一次** `_emit_busy_interruption`（reason=`monitor_busy_without_progress`）。
- **中断响应**（`_on_monitor_interrupted`, `ui.py:1605`）：代际/会话校验→若被 A 端任务占用（`_monitor_blocked_by_a_side`）→**让出回复包装、继续停滞检测与自动续接**（记 owner）；`last_finish=="length"`→转人工（截断是真最终回复，不自动续接）；已有 auto/continuing 在跑→忽略重复；`auto_count<3 且 未禁用`→`_begin_auto_monitor_continue`；否则 `_monitor_stall_manual`。
- **自动续接 3 次**（`_begin_auto_monitor_continue`→`MonitorAutoContinueTask`）：`auto_count+=1`、`auto_pending=True`、显示「自动续接 n/3」→`MonitorAutoContinueTask` 等 `interval=10s`（可被 stop 取消）后发 `MONITOR_CONTINUE_PROMPT`：
  - 成功→`_on_auto_continue_succeeded`：`auto_pending/interrupted=False`、置 `busy_reset_event`（poller 观察新 user 消息重置计时）、**保留 auto_count**（下次整段卡死用下一档，只有“包装到最终回复”或“停止”才清零）。
  - 失败（传输类 `transport`）→`_confirm_auto_continue_progress`（`MonitorRecoveryQueryTask` 复查）：`progress`→该次**不计**（回退 auto_count、继续监听）；`no_progress`→计入，`attempt<3`→再发下一档，否则→`_monitor_stall_manual`（3 次耗尽）。
  - 失败（不可重试：400/Aborted/会话不存在/认证/意外）→`auto_disabled=True`、转人工（本会话不再自动续接）。
- **3 次耗尽/转人工**（`_monitor_stall_manual`）：置 `_oc_monitor_interrupted=True`、`auto_disabled=True`、状态「自动恢复3次仍未完成，请人工继续或停止」，`continue/stop` 按钮点亮。
- **收到最终回复**（`_on_monitor_reply`, `ui.py:1894`）：被 A 端占用→让出（记 `_oc_monitor_yielded`）；否则去重（`is_message_wrapped` / seen）后 `wrap_response(text, manual-{uuid}, V1, round=0, max=1)`→best-effort `save_reply`+`registry.mark(COMPLETED)`→`write_response`→`mark_message_wrapped`→清 interrupt/continuing/transport 状态 + **清零 auto 预算**（下一段卡死从 1/3 重新开始）。

### 4.9 A 端优先级 / 监控让出（invariant 2/4/6/7）
- `_register_a_side_claim`：仅 OPENCHAMBER 任务登记占用（REASONIX 任务从不挡监控）；登记 `workdir or 默认目录` 的 `directory_key`；无目录→`_a_side_oc_pending=True`（保守让出，直到任务被识别或结束）。
- `_on_session_started`：任务会话/目录加入 in-flight 集合；`_a_side_session_owner[session]=task_id`（监控让出/续接日志可审计）；`_a_side_oc_pending=False`。
- `_monitor_blocked_by_a_side`：A 端活跃且（oc_pending 或 监控会话∈in-flight 或 监控目录∈in-flight）→True。
- `_finish_task`：清所有 in-flight 集合与 owner、`_current_a_task_id=None`（B 端任务到终态才释放，监控恢复全权）。

### 4.10 自动轮换会话（`SessionRotation`, `session_rotation.py`）
- **计数**：`note_auto_success(dir)`（仅 OPENCHAMBER 自动任务成功时调）：未开启→不计数；`_counts[key]+=1`，`>= threshold` 返回 True（**不清零**，失败重试保住里程碑）。`_task_succeeded` 里触发 `_start_auto_rotation`（`ui.py:2574`）。
- **命名**：`rotation_sequence_label(N)`（`session_rotation.py:27`）→中文序数：1→第一个、10→第十个、11→第十一个、20→第二十个、100→第一百个；**10/11/19 无百位时读 十/十一/十九（十前不加一），110 读 一百一十（有百位才在一十前加一）**。新会话标题 = `f"{base} - {label}"`（分隔符 `" - "`）。
- **基础名优先级**（`_base_title`）：**已持久化 base（`auto_rotate_base_titles[key]`）> 提示（当前固定会话标题，先 `strip_rotation_suffix` 去掉旧 ` - 第N个` 后缀，防止嵌套 “Task 14H - 第二个 - 第一个”）> 兜底 `任务会话`**。
- **`rotate()`**：`sequence = auto_rotate_sequences[key]+1`→`create_session(标题, dir)`→（可选）`_inherit_auto_accept`（best-effort 复制上一会话的“自动接受权限”到新会话，快照/设置失败只记日志不中断）→写 `openchamber_sessions[key]=新id`、默认目录同步 `openchamber_session_id`→**只有创建并保存成功后**才提交 `auto_rotate_sequences[key]=sequence` 与 `auto_rotate_base_titles[key]=base` 并 `settings.save()`（创建失败两者都不动）。
- **计数何时清零**（`reset`/`reset_all`）：开关切换、手动切换会话、手动新建会话、项目目录改变、成功轮换、新会话重试成功（`_task_succeeded` 里 `self._rotation.reset(outcome.directory)`）。
- **`strip_rotation_suffix`**（`session_rotation.py:60`）：`re.fullmatch(r"^(?P<base>.+?)\s*-\s*第[零一二三四五六七八九十百]+\s*个$")`，匹配则取 `base`，否则原样 trim。
- **UI 触发**（`_start_auto_rotation`）：`_rotation_pending` 去重；从 `_session_combo` 当前标签提取 base 提示（去 `（session_id）` 后缀）→起 `RotateSessionTask`→`_rotation_succeeded`：`reset(dir)` + `_adopt_openchamber_session(新id)`（选进下拉+刷新列表）；`_rotation_failed`：计数保留，下次成功重试。

**消息结构**：`{"info": {id, role, time:{completed:int}, finish, error, model}, "parts":[...]}`；`_role`/`_message_id`/`_text_parts`（排除合成/忽略 part）/`_tool_call_names`。

### 4.12 启动对账 `reconcile_stale_task`（`relay.py:280`）
对上次运行遗留的 `RECEIVED/PROCESSING` 记录（**只读**，主线程再写表）：
- 非 OPENCHAMBER / 无 session / 无 dir → `RECOVERY_REQUIRED`（无法事后核实）。
- `verify`+`messages` 失败 → `RECOVERY_REQUIRED`。
- 用 `[AI_RELAY_TASK_ID: 原id]` 定位 user 消息：0 条→未找到；>1 条→歧义（不猜）。
- `locate_round` 失败 / 无 assistant 回复 / `has_pending_user_action` → `RECOVERY_REQUIRED`。
- 最后一条 assistant：`info.error`→`FAILED`；未完成→`RECOVERY_REQUIRED`；`finish=="length"`→`FAILED`（截断）；`finish!="stop"`→`RECOVERY_REQUIRED`；`extract_final_text` 空→`RECOVERY_REQUIRED`；否则→`COMPLETED`（带回 `final_text` + `reply_message_ids`）。
- UI（`_on_recovery_done`, `ui.py:2814`）：COMPLETED→`_recovered_response` 按**原 id** 包装 → `save_reply` + `mark_message_wrapped` + `mark(COMPLETED)`；**仅当本运行没产生更新的回复**才写剪贴板，否则存 `_pending_recovered_reply` 待 lane 空闲再补写（旧任务回复不覆盖新任务）。FAILED→`mark(FAILED)`；其它→`mark(RECOVERY_REQUIRED)`。对账整体失败（`_on_recovery_failed`）→**所有**遗留记录置 `RECOVERY_REQUIRED`。
- 快照隔离（`_startup_stale_task_ids`, `ui.py:944`）：只对“窗口构造前”就存在的非终态记录做对账；本次运行已认领（auto 拾取/直送）的 RECEIVED 是 in-flight，绝不当 stale。

### 4.13 FIFO 队列 + 认领（`_accept_a_side_task` / `_start_next_queued_task`, `ui.py:2152/2248`）
- 收到新 A 端 TASK：`sequence=registry.next_sequence()`；`_busy 或 关窗中`→`mark(QUEUED, raw_message, sequence, received_at)`（**入队不拒绝**），提示排队位置；否则→`mark(RECEIVED,…)` → `_launch_a_side_task`（`_busy=True`、`generation+=1`、`_register_a_side_claim`、起 `RelayTask`）。
- **每个**任务终态都经 `_finish_task` 统一出口：清 in-flight、`_set_controls_enabled(True)`、补写 `_pending_recovered_reply`、`QTimer.singleShot(0, _start_next_queued_task)`。
- `_start_next_queued_task`：`QUEUED` 按 `sequence`（回退 `received_at`）取头部；`raw_message` 缺失→`RECOVERY_REQUIRED`（防一条坏记录卡死队列）；协议解析失败→`FAILED`；否则 `mark(RECEIVED)`（保留 raw/sequence）→重跑。**从持久化 body 重执行，不再从剪贴板重发**。
- 队列在关窗 / 启动对账未完成时不推进。

### 4.14 终态保护（`TaskRegistry`, `task_registry.py`）
- `TERMINAL_STATES = {COMPLETED, STOPPED_BY_USER, FAILED}`。
- `mark`（无条件写，主线程对账/认领/人工包装用）；`mark_if_state`（仅在 `expected_states` 时写，原子）；`mark_if_active`（**已任一终态则 no-op**，普通 worker 每次状态写都用它）；`mark_reentry`（显式重入，允许从终态再走：手动继续 / 新会话重试 / 停止中断任务 / 启动对账）。
- `_apply`：只保留 `EXTRA_FIELDS`（executor/session_id/directory/reply_file/requested/resolved/actual_model/model_note/raw_message/sequence/received_at/completion_source）+ `state` + `error`；`_save` 写临时文件再原子 `replace`，失败重试 3 次（Windows 上杀软/索引器可能瞬时锁文件）。
- **目的**：迟到/被取代的 worker 永不把已 `COMPLETED/STOPPED/FAILED` 的任务改回 `PROCESSING` 或另一个终态。

## 第 5 章 接收流程（“怎么接收”总述）

### 5.1 B 端接收 A 端 TASK
```
A 端写剪贴板(AI_RELAY/1 TASK)
  → ClipboardListener._on_changed（去重/自写过滤）
  → task_received(text) → _on_clipboard_text (ui.py:2019)
      1) looks_like_relay_message? 否→忽略
      2) parse_message → RelayProtocolError → _show_error
      3) message_type != TASK → 忽略
      4) registry.record(id) 存在? → _answer_duplicate_task（回已有状态/回复，永不重跑）
      5) 否则 _accept_a_side_task → 落盘 QUEUED/RECEIVED + sequence
          - 忙/关窗 → 入队
          - 空闲 → _launch_a_side_task → RelayTask.process
```

### 5.2 B 端向 A 端交 RESPONSE
- **成功**：`_task_succeeded` → `write_response(response)`（response 由 `wrap_response(final_text, 原id, …)` 生成）。
- **失败/停止**：`_task_failed`/`_stop_task` → 取 `failure_response`（由 `_finalize_failure` 用 `_failure_body` 生成，`IN_REPLY_TO=原id`）→ `write_response`。
- **监控/人工包装**：`_on_monitor_reply` / `_wrap_*` → 同样 `write_response`。
- **恢复回复**：`_recovered_response`（原 id 包装）→ 空则写，忙则存 `_pending_recovered_reply` 待补写。
- A 端侧：把剪贴板里的 `AI_RELAY/1` / `----- AI_RELAY_BEGIN -----` 文本按其 `IN_REPLY_TO/TASK_ID` 匹配到对应任务即可；`TYPE:RESPONSE` 表示是结果，`SOURCE:EXECUTOR` 表示来自 B 端。

### 5.3 重复 TASK_ID 的应答（`_answer_duplicate_task`, `ui.py:2109`）
- 记录态 `COMPLETED/FAILED/STOPPED_BY_USER`→`load_reply(id)` 直接回已保存回复；
- 无回复且 `RECEIVED/PROCESSING`→回“正在执行中，完成后返回，勿重复发送”（`wrap_response` 用原 format/round/max_rounds）；
- 其它→回“当前状态为 X[, 错误: …]”；
- 一律 `write_response` 绑定**原 id**。

### 7.2 `data/tasks.json`（`TaskRegistry`，`task_registry.py`）
- 结构：`{task_id: {state, error?, <EXTRA_FIELDS>}}`。
- 状态值：`QUEUED / RECEIVED / PROCESSING / COMPLETED / FAILED / STOPPED_BY_USER / RECOVERY_REQUIRED`。
- `EXTRA_FIELDS`：`executor, session_id, directory, reply_file, requested_model, resolved_model, actual_model, model_note, raw_message, sequence, received_at, completion_source`。
- `raw_message`（完整协议文本）让 `QUEUED` 任务重启后可重执行；`sequence`（字符串）是单调认领序；`completion_source` ∈ `auto_relay`/`manual_wrap`。

### 7.3 `data/replies/` 与日志
- 回复文件：`rel_{sha256(task_id)}.response.txt`（hash 命名，任意 task_id 安全：遍历/绝对路径/盘符/保留名/非法字符/CJK 都收敛成同一 hex 名）；`load_reply` 依次尝试 registry 记录路径 → 当前 hash 名 → legacy `{task_id}.response.txt`，且路径必须解析在 replies 目录内。
- `data/relay.log`：`logging` 输出（`LOGGER = logging.getLogger("ai_relay_b")`），记录监听开始/停止、任务认领/终态、自动恢复、监控中断/续接、模型拒绝、传输重试等审计行。
- 运行时数据目录由 `core/runtime_paths.data_dir()` 提供。
